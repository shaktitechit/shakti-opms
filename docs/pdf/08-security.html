2. Authentication

Mechanism

  • JWT signed with shared JWT_SECRET across services
  • Passwords hashed with bcrypt (bcryptjs)
  • Token TTL via JWT_EXPIRES_IN (example default 7d)
  • Optional MASTER_PASSWORD: break-glass login as any user if set — must be empty in production

Login flow

sequenceDiagram participant C as Client participant Auth as auth-service participant API as Domain API C->>Auth: POST /api/auth/login Auth-->>C: JWT (+ user claims) C->>API: Authorization: Bearer JWT API->>API: verify signature / expiry API->>API: load/attach req.user API->>API: portal / role gate API-->>C: 200 resource or 401/403

Obtain token

POST /api/auth/login
Content-Type: application/json

{ "email": "user@example.com", "password": "********" }

Available on auth-service (:7003) or via opms-backend proxy (:7001/api/auth/login).

Session introspection

GET /api/auth/me
Authorization: Bearer <token>

Frontend session handling

App Primary storage Notes
app-frontend shakti.app.session + cookies SSO hub; launches peers with ?token=
opms-frontend medica.auth + cookies Consumes SSO token
user / lead / work planner per-app shakti.*.session Shared cookie names used for middleware gates

Risk note: JWT in query string for SSO is convenient but can leak via Referer/logs/history. Prefer short-lived handoff and strip token after consume (apps attempt strip after bootstrap).

3. Authorization (RBAC)

Layers

  1. Authenticated — valid JWT
  2. Portal membership — user.portals[] contains required portal_code
  3. access_roles — role string must match portal gate (admin bypass where coded)
  4. Handler-level checks — department/workflow rules for specific actions
  5. Soft-delete routes — authenticated (+ OPMS portal) on many trash/restore endpoints

4. Transport & edge security

nginx (production pattern)

  • TLS 1.2/1.3 via nginx/snippets/ssl-params.conf
  • HSTS and security headers in ssl snippets
  • Let's Encrypt cert paths for *.spspl.com / *.medicaent.in
  • HTTP → HTTPS redirect after cert bootstrap
  • SSE-specific proxy settings for notification streams

CORS

Configured via CORS_ORIGINS / service CORS settings. Production frontends must be listed. Incorrect CORS is a browser-enforced issue, not a substitute for authz.

Docker network

Services communicate on the Compose bridge using internal URLs (http://auth-service:7003, etc.). Assume network trust inside the compose network for some internal endpoints (see §6).

Documented carefully for threat modeling. Verified from route files.

Surface Auth Risk

flowchart LR Internet --> Nginx Nginx --> PublishedPorts[Host published API ports] PublishedPorts --> Weak[Weakly protected routes] Weak --> Impact[Data injection / file access / spam]

Hardening (recommended, not implemented in-repo):

  • Bind internal-only routes to Docker network (do not publish message/notification internal ports publicly where avoidable)
  • Add requireAuth or shared service token to internal notification/create routes
  • Add auth to terms and attachments routers
  • Add login rate limiting / lockout
  • Enable Redis AUTH and avoid publishing Redis on host

10. Incident checklist (ops-oriented)

  1. Rotate JWT_SECRET → forces re-login everywhere (coordinate downtime)
  2. Rotate Mongo, File API, Graph, WhatsApp, VAPID, webhook secrets
  3. Clear MASTER_PASSWORD in production env
  4. Review nginx access logs for scraping of public/weak routes
  5. Restart services after secret rotation: docker compose --env-file .env.docker up -d
  6. Rebuild frontends if any NEXT_PUBLIC_* changed

Module: Authentication

Purpose

Authenticate users, issue JWTs, expose current user profile, and support password change.

Actors

Any user with an active auth-service account; App Frontend and all portal frontends.

Preconditions

  • auth-service running and Mongo reachable
  • User exists with password hash; is_active true (Inferred inactive users rejected — verify service)

Workflow

flowchart TD A[Open login page] --> B[Submit email/password] B --> C{Valid?} C -->|No| D[Show error] C -->|Yes| E[Issue JWT] E --> F[Store session in browser] F --> G[Navigate dashboard/portal] G --> H[Optional SSO ?token= to other app]

Business Rules

  • Shared JWT_SECRET across services
  • Optional MASTER_PASSWORD can authenticate as any user if set — must be empty in production

Validations

Email/password required on login (controller-level).

Permissions

Login public; /me and change-password require auth.

Exceptions / Errors

401 invalid credentials; 401/403 on protected routes without/with wrong token.

Related APIs

  • POST /api/auth/login
  • GET /api/auth/me
  • POST /api/auth/change-password

Related DB

User, Role, Portal, Department, CompanyInfo (auth-service)

Related UI

app-frontend /, portal /login pages

Dependencies

auth-service; MongoDB; frontends
